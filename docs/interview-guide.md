# Interview Guide

Every answer below is split into a **technical** framing and a **business/consulting** framing, since
this project sits deliberately at the intersection.

## 1. What problem does the project solve?

**Technical**: Turning an unstructured policy document plus an unstructured evidence corpus into a
structured, source-cited, cross-checked analysis — without a single LLM call hallucinating its way
through eight distinct analytical tasks at once.

**Business**: A consulting team's first pass on a new policy/programme — objectives, evidence, stakeholders,
risks, benchmarks, a 90-day plan — usually takes days of analyst time and varies in quality by who does it.
This produces a defensible first draft in minutes, with every claim traceable to a source or explicitly
flagged as an assumption, so a human reviewer's time goes to judgment calls, not first-draft assembly.

## 2. Why did you use RAG?

**Technical**: The agents need grounded access to *this specific* evidence base — an LLM's parametric
knowledge doesn't contain your organization's benchmark case studies or risk precedents, and asking it to
improvise them is exactly how citations get fabricated. RAG retrieves real chunks with real document/page
metadata and forces the model to work from them.

**Business**: A recommendation with no source is a guess dressed as an insight. RAG is what lets the
output say "[risk_case_study_prior_rollout.txt, p.1]" instead of "studies show" — the difference between
something you can defend to a client and something you can't.

## 3. Why did you use CrewAI?

**Technical**: `Agent`/`Task` primitives with `output_pydantic` gave schema-constrained, validated
structured output per agent for free, and an LLM-provider-agnostic model string. I did *not* end up using
its `Crew.kickoff()` orchestration for the main pipeline — see Q19.

**Business**: It's a coordination framework, not magic — the value is forcing each specialist's output
into a checkable shape, the same reason a consulting engagement splits into distinct workstreams with
named owners instead of one generalist trying to hold everything in their head.

## 4. Why multiple agents instead of one agent?

**Technical**: Different responsibilities need different grounding, different failure modes to guard
against, and — critically — the Challenge Agent needs to be a genuinely separate agent from the ones it's
critiquing, or "review" is just the same model agreeing with itself.

**Business**: This mirrors how a real engagement works — a policy analyst, a researcher, a risk lead and
an independent QA reviewer are different people with different incentives, not one person wearing four
hats and grading their own homework.

## 5. What does each agent do?

See [docs/agent-design.md](agent-design.md) for the full breakdown (7 analysis agents + 1 synthesis
agent, in order: Policy → Evidence → Stakeholder → Risk → Benchmark → Implementation → Challenge → Synthesis).

## 6. How does information move between agents?

**Technical**: Each agent's `Task.execute_sync()` returns a `TaskOutput` with a validated Pydantic object
(`.pydantic`) and raw text (`.raw`). Downstream tasks receive the upstream raw JSON embedded directly in
their task description — not CrewAI's internal `context=[Task, Task]` chaining, because the pipeline is
orchestrated manually (see Q19). The Policy Analyst's `.objectives`/`.assumptions` literally become the
Evidence Analyst's retrieval queries — a real hand-off, not decoration.

**Business**: Downstream work builds on validated upstream conclusions, the way a risk assessment should
reference the stakeholder map that was already agreed, not redo stakeholder analysis from scratch.

## 7. How do you prevent hallucination?

**Technical**: (a) every evidence/benchmark claim must cite a `SourceCitation` the agent was told exists
in its supplied context; (b) agents are instructed to output "Insufficient evidence in the available
knowledge base" rather than force a citation; (c) the Challenge Agent independently checks for exactly
this failure mode; (d) the synthesis step (the one place with no retrieval grounding) is explicitly
told not to introduce any fact not already present in the material it's given, and the rest of the final
report is assembled in Python from structured objects, not regenerated by an LLM at all.

**Business**: No single control eliminates hallucination risk — the honest answer is "reduced and
checked, not solved," which is why every report carries "AI-generated analysis — verify critical
decisions against primary sources."

## 8. How do you evaluate the RAG system?

See [docs/evaluation.md](evaluation.md). Short version: hit-rate@k, MRR and a negative control on a
15-question hand-written set against the demo corpus — real numbers, explicitly scoped as not
generalizable. **Technical honesty point**: I did not build an automated generation-groundedness score,
and I can explain why (see evaluation.md) rather than quote a number I don't trust.

## 9. How do you validate citations?

**Technical**: Structurally, every citation the *final report* carries in `sources` is built in code from
actual `retrieve_evidence()` rows (`app/crew/runner.py`), not just trusted from agent output — so the
master Sources tab can't contain a document that isn't really in the vector store. Citations *inside*
individual `EvidenceFinding.sources` are agent-generated and constrained by the prompt to match the
supplied context, but not independently re-verified against the store — a named limitation (see Q20).

**Business**: "Click a citation to see the retrieved passage" (Sources tab) is the actual verification
mechanism a reviewer would use — trust, but let them check in one click.

## 10. What happens when evidence conflicts?

**Technical**: `EvidenceFinding.contradiction` is an explicit optional field the Evidence Analyst can set
per claim, and the prompt asks for contradictory evidence, not just supporting evidence.

**Business**: Surfacing disagreement in the evidence is more useful than silently picking a side —
a client needs to know when their own prior programmes point in different directions.

## 11. Why not fine-tune the model?

**Technical**: Fine-tuning changes style/behavior/task-pattern; it doesn't give the model access to a
changing, organization-specific evidence base, which is exactly what's needed here. RAG is the correct
tool for "ground answers in *these* documents."

**Business**: Fine-tuning is also a fixed, stale snapshot — a new policy document or a new benchmark case
study needs to be usable immediately, not after a retraining cycle.

## 12. Why not use a simple RAG chatbot?

**Technical**: A single retrieve-then-generate call can't hold seven distinct analytical structures
(objectives, evidence table, stakeholder matrix, risk register, benchmarks, roadmap, review) with
different grounding needs and cross-checks in one coherent, validated output — you'd get an unstructured
wall of text or a schema so large the model quietly drops fields.

**Business**: A chatbot answers one question at a time. A transformation advisory report needs to hang
together as one coherent deliverable where the roadmap visibly responds to the risks and stakeholders
already identified — that's a document, not a chat.

## 13. What are the limitations?

See README §14 and the "Known limitations" sections in `docs/architecture.md`/`docs/rag-design.md` in
full. Headlines: in-memory job store (no restart survival), no hybrid retrieval/reranking, no access
control, evaluation numbers are demo-corpus-only, citations inside individual findings aren't
independently re-verified against the store.

## 14. How would you deploy this in an enterprise?

**Technical**: Persist job state (Redis/Postgres) instead of in-memory; move ChromaDB to a managed vector
DB or Postgres+pgvector for durability and backup; put the API behind auth; run the analysis pipeline as
a proper background worker (Celery/RQ) instead of a raw Python thread; add request-level rate limiting.

**Business**: Enterprise deployment is mostly about *reliability and auditability* guarantees a POC
doesn't need — who ran this analysis, on what document version, with what model version, and can that be
reproduced six months later for an audit.

## 15. How would you secure confidential government data?

**Technical**: Document-level access control tied to auth; encryption at rest for the vector store and
uploaded files; audit logging of every retrieval (who queried what, when — the logging scaffold in
`app/utils/logging.py` already logs queries/stages/latency, but not per-user); network isolation for any
on-prem deployment; a private/self-hosted embedding model and LLM if data can't leave the environment at
all (the architecture already supports swapping providers via `LLM_PROVIDER`, though not yet a fully
local model).

**Business**: The single biggest change from this POC to something touching real classified/sensitive
material: no data should reach a third-party LLM API without an explicit data-handling agreement, and
some deployments would require a self-hosted model entirely — a real cost/capability trade-off to raise
with the client explicitly, not assume away.

## 16. How would you reduce cost?

**Technical**: Cache retrieval results per policy hash; use a cheaper/smaller model for high-volume
agents (e.g. stakeholder mapping) and reserve a stronger model for the Challenge Agent; batch or skip
the benchmark retrieval pass when the KB has no benchmark-shaped documents; only run the revision loop
when the reviewer's severity threshold is actually crossed, not on every minor issue.

**Business**: Not every workstream needs frontier-model quality — matching model tier to task criticality
is itself a cost decision, same as staffing a junior vs. senior consultant to different parts of an
engagement.

## 17. How would you reduce latency?

**Technical**: Run independent agents (Stakeholder, Risk analysis inputs are already available in
parallel after Evidence completes) concurrently instead of strictly sequentially; stream partial results
to the UI instead of polling for a single final report; cache embeddings for unchanged documents.

**Business**: For a synchronous "wait and watch" demo, showing live progress (already implemented) matters
as much as raw speed — a client experience problem, not just a systems one.

## 18. How would you scale it?

**Technical**: Move job state out of process memory; run multiple backend workers behind a load balancer;
move the vector store to a managed service; consider a real task queue instead of a raw background thread
per request.

**Business**: Scale here mostly means *concurrent engagements*, not raw request volume — the growth path
is "more analysts running more policies through this at once," which maps directly to the worker/queue
changes above.

## 19. Why CrewAI instead of LangGraph?

**Technical**: CrewAI's `Agent`/`Task`/`output_pydantic` gave the fastest path to validated structured
agent output with minimal boilerplate for a 7-agent linear-ish pipeline. I explicitly did **not** end up
using CrewAI's own orchestration (`Crew.kickoff()` with `Process.sequential`) for the main pipeline — the
revision loop needs to selectively re-run specific upstream agents based on the reviewer's structured
output, which is a conditional-branching need CrewAI's built-in sequential process doesn't support. I
orchestrate manually in `app/crew/runner.py` by calling `Task.execute_sync(agent=...)` directly per step.
A graph framework like LangGraph is arguably a more natural fit for *that* control-flow need (explicit
nodes/edges/conditionals) — a legitimate alternative I'd consider if this workflow's branching logic grew
more complex than the current single-file bounded loop.

**Business**: Tool choice should follow the actual control-flow complexity of the problem — this
workflow's complexity was modest enough that a hand-rolled loop stayed more explainable than adopting a
heavier graph framework, but that calculus changes as the workflow grows.

## 20. What would you change in a production implementation?

In priority order: (1) persist job state and move off in-memory storage; (2) add independent citation
verification against the vector store, not just prompt-level constraint; (3) add authentication and
document-level access control; (4) replace the demo evaluation set with a larger, held-out one and add
automated generation-quality scoring; (5) move to hybrid retrieval + reranking; (6) add real observability
(structured logs are already there — add tracing/metrics dashboards on top).
