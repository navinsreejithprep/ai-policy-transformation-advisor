# Architecture

## Core pattern

RAG supplies grounded evidence. Seven CrewAI agents (plus a synthesis agent) each own one analytical
responsibility. Every agent-to-agent hand-off is a validated Pydantic object (`app/models/schemas.py`),
not free text — see `output_pydantic=` on every `Task` in `app/crew/tasks.py`.

## Data flow

```text
Policy text (user input)
    |
    v
[Policy Analyst] --output_pydantic--> PolicyAnalysis
    |  .objectives + .assumptions become retrieval queries
    v
retrieve_evidence() x N queries --> ChromaDB (cosine, top_k, relevance-thresholded, deduped)
    |
    v
[Evidence Analyst] --output_pydantic--> EvidenceReport (findings cite real doc/page, or evidence_gaps)
    |
    v
[Stakeholder Analyst] --output_pydantic--> StakeholderMatrix
    |
    v
[Risk Analyst] --output_pydantic--> RiskRegister
    |
    v
[Benchmark Analyst] --output_pydantic--> BenchmarkReport   (separate retrieval pass, benchmark-framed queries)
    |
    v
[Implementation Strategist] --output_pydantic--> ImplementationPlan (every item's `linked_to` must
    |                                             reference a prior risk/stakeholder/evidence-gap)
    v
[Independent Challenge Reviewer] --output_pydantic--> ReviewResult (PASS | NEEDS_REVISION + issues)
    |
    +--- NEEDS_REVISION, cycle < REVISION_MAX_CYCLES (default 2) -----+
    |         re-run only the specific flagged agents with the        |
    |         reviewer's feedback appended to their original context, |
    |         then re-run the reviewer                                |
    |    <---------------------------------------------------------- +
    v  PASS, or cycles exhausted
[Synthesis Advisor] --raw text only--> executive_summary (<=500 words, no new facts allowed)
    |
    v
FinalReport assembled in Python from the structured objects above
(sources deduped across evidence + benchmark retrieval, revision_log recorded)
    |
    v
JobStore (in-memory) <-- FastAPI background thread
    |
    v
GET /analysis/{id} (poll) -> GET /analysis/{id}/report -> Next.js dashboard
```

## Why manual orchestration instead of `Crew.kickoff()`

The natural CrewAI approach is one `Crew(agents=[...], tasks=[...], process=Process.sequential)` and a
single `.kickoff()`. Two things make that insufficient here:

1. **`Crew.kickoff()`'s return value is the *last* task's output only** (available per-task via
   `CrewOutput.tasks_output`, but not assembled into anything). The original version of this project
   actually shipped this exact bug: `POST /analysis` returned the Challenge Agent's *critique* of the
   report, not the report itself, because the reviewer was the last task in the sequence. Manual
   orchestration (`app/crew/runner.py`) captures every task's structured output explicitly and builds
   the `FinalReport` from all of them.
2. **The revision loop needs to selectively re-run individual agents**, not the whole pipeline, and
   CrewAI's `Process.sequential` has no conditional-branching primitive for that (`Process.hierarchical`
   delegates control to a manager LLM, which trades explainability for flexibility we didn't need).
   Running each `Task.execute_sync(agent=...)` directly (confirmed to work standalone against
   CrewAI 1.15.x — see the docstring in `app/crew/tasks.py`) gives full, bounded, inspectable control:
   the reviewer's `ReviewIssue.target_agent` field tells the runner exactly which upstream task to
   re-execute with the reviewer's feedback appended to its original context.

This is a documented **engineering trade-off**: less "free" CrewAI machinery, more explicit control flow
that's easy to explain and reason about in an interview. A production version processing much larger
workflows might revisit this with `Process.hierarchical` or a graph framework (LangGraph, etc.) once the
branching logic outgrows a single Python file.

## Why the Synthesis Advisor only writes the executive summary

Every other section of the final report (policy analysis, evidence table, stakeholder matrix, risk
register, benchmarks, roadmap, KPIs, sources) is assembled in plain Python from the structured Pydantic
objects the upstream agents already produced — not regenerated by an LLM. This means nothing in the
report *except* the 500-word executive summary can introduce a new hallucinated fact at the synthesis
step, and the summary agent is explicitly instructed not to introduce anything not already present in
the material it's given.

## Important limitations

- This is a bounded, explainable workflow, not an autonomous agent — the revision loop is capped at
  `REVISION_MAX_CYCLES` (default 2) specifically to avoid an infinite loop.
- Job state is in-memory (`app/services/jobs.py`) and won't survive a backend restart — fine for a POC,
  called out explicitly in the README as something a production version must change.
- See `docs/rag-design.md` for retrieval-specific limitations (no hybrid search, no reranking).
